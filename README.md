# BudgetIQ Power BI Dashboard

A three-page Power BI dashboard that analyses personal spending, built on the same transaction data model as my South African personal finance app, **BudgetIQ**. It answers three questions: *Where does the money go? Are we on budget? What looks unusual?*

> **All data in this repo is synthetic.** It was generated by a script to mirror the structure of BudgetIQ's `transactions` table. No real people, accounts or transactions are used.

## Data

Two CSV files in the root of this repo:

**`transactions_synthetic.csv`** (733 rows, 727 after cleaning): same columns as BudgetIQ's `transactions` table.

| Column | Description |
|---|---|
| `id` | Unique row ID (UUID) |
| `user_id` | Fake user ID (one synthetic persona) |
| `date` | Transaction date |
| `description` | Bank-statement text, mixed English/Afrikaans, inconsistent casing, some truncated |
| `amount` | Negative = money out, positive = money in |
| `category` | One of 23 BudgetIQ categories |
| `created_at` | Upload timestamp (one batch per month) |

**`budgets_synthetic.csv`**: one monthly budget (R) per spending category.

**Deliberate data-quality problems** were built in so the cleaning and anomaly pages have real work to do:
- 6 exact duplicate transactions
- 15 grocery/dining rows wrongly categorised as "Other"
- Inconsistent casing and truncated merchant names
- Four planted outliers (laptop, unknown merchant, flights, dishonoured debit-order fee)

`generate_synthetic_data.py` recreates both files (seeded, so the output is reproducible).

## Data preparation (Power Query)

1. **Fixed the `amount` type.** It loaded as text, so it was converted to Decimal Number using the **English (United States)** locale, because the file uses a full stop as the decimal separator and South African regional settings expect a comma.
2. **Removed duplicates** on `date + description + amount` (not the `id`, which is unique on every row). 733 → 727 rows. *Assumption: rows identical on those three fields are double-posted entries, which is the usual cause when a statement is uploaded twice.*
3. **Added a `Type` column** (Income / Spend / Savings / Transfer) so that salary, transfers between accounts and savings are not counted as spending.

## Data model

```
Date (calendar table) ──1──────*── transactions_synthetic ──*──────1── budgets_synthetic
   Date[Date] → transactions[date]        transactions[category] ← budgets[category]
```

- Both relationships are **many-to-one, single direction**.
- `Date` is a calculated table (365 days, Oct 2025 – Sep 2026) marked as the date table. `Month Year` is sorted by `YearMonth` so months appear in calendar order instead of alphabetically.

## DAX

**Measures**

```dax
Total Income = CALCULATE ( SUM ( transactions_synthetic[amount] ), transactions_synthetic[Type] = "Income" )

Total Spend  = -1 * CALCULATE ( SUM ( transactions_synthetic[amount] ), transactions_synthetic[Type] = "Spend" )

Net Savings  = [Total Income] - [Total Spend]

Savings Rate = DIVIDE ( [Net Savings], [Total Income] )

Budget =
CALCULATE (
    SUM ( budgets_synthetic[monthly_budget] ),
    KEEPFILTERS ( budgets_synthetic[category] <> "Savings" )
) * DISTINCTCOUNT ( 'Date'[YearMonth] )

Variance         = [Budget] - [Total Spend]      -- positive = under budget
% of Budget Used = DIVIDE ( [Total Spend], [Budget] )
```

**Calculated columns** (used for the anomaly flag)

```dax
Spend Amount = IF ( transactions_synthetic[Type] = "Spend", -1 * transactions_synthetic[amount] )

Is Unusual =
VAR _Amt = transactions_synthetic[Spend Amount]
VAR _Avg = CALCULATE ( AVERAGE ( transactions_synthetic[Spend Amount] ),
                       ALLEXCEPT ( transactions_synthetic, transactions_synthetic[category] ) )
VAR _Std = CALCULATE ( STDEV.P ( transactions_synthetic[Spend Amount] ),
                       ALLEXCEPT ( transactions_synthetic, transactions_synthetic[category] ) )
RETURN IF ( NOT ISBLANK ( _Amt ) && _Amt > _Avg + 2 * _Std, 1, 0 )
```

**Design decisions worth knowing**
- **The `-1 *` in Total Spend:** spending is stored as negative numbers. Flipping the sign lets the report show spend as a positive figure and keeps `Net Savings` a simple subtraction.
- **`KEEPFILTERS` in Budget:** without it, the "not Savings" condition inside `CALCULATE` overwrites the per-category filter from the chart, and every category shows the full-year total budget. `KEEPFILTERS` combines the two filters instead.
- **`DISTINCTCOUNT` of months:** the budget is a monthly amount, so it is multiplied by the number of months in the current selection. Budget and spend therefore always cover the same period, whether one month or twelve is selected.
- **Transfers and Savings are excluded from spend.** Moving money between your own accounts is not an expense. Savings contributions are treated as a use of surplus, so they are not included in `Total Spend`.

## Dashboard pages

1. **Overview**: KPI cards (income, spend, net savings, savings rate), monthly income vs spend, spend by category, and a month slicer.
2. **Budget vs Actual**: budget vs spend by category, and a table with variance and % of budget used (overspends highlighted red).
3. **Insights**: unusual transactions, flagged when spend is more than 2 standard deviations above the category average, with a table of the flagged items and a count by category.

The month slicer is synced across all pages.

## Limitations

- The data is synthetic, so the findings illustrate the method and are not conclusions about real spending behaviour.
- The anomaly rule is simple. It flags how unusual an amount is *for its category*, not how much it matters in rand: four Food & Dining items are flagged for being a little above normal, while the R14,999 laptop is a single Shopping flag. A rule based on rand impact or a rolling window would refine it.
- Standard deviation is sensitive to the outliers it is trying to find, because a very large item inflates its own category's threshold.
- Budgets are one fixed monthly figure per category, with no seasonality, so December and similar months look worse than they are.
- The duplicate rule can remove legitimate repeat purchases (for example, two identical parking payments on one day). A production version would flag suspected duplicates for review instead of deleting them.
